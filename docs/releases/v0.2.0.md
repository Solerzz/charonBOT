# Charon v0.2.0 — Setup e join-to-create

## Entregas

- `/setup init` privado, restrito a Administrador ou Gerenciar Servidor +
  Gerenciar Canais, com revalidação nas ações.
- Vários Voice Creators por servidor, cada um com categoria e preferência de
  comandos independentes. Adicionar **seleciona um canal de voz existente** e
  uma categoria; renomear altera esse canal, não cria outro.
- Remoção com confirmação e exclusão lógica, preservando canal e salas.
  Reconfigurar o mesmo canal restaura UUID/histórico/preferência no mesmo servidor.
- Salas públicas, sem limite, criadas ao entrar no Voice Creator; reutilização
  da sala ainda acompanhada do proprietário no servidor quando possível.
- Nome inicial de até 11 grafemas a partir de atividade `Playing` disponível ou
  nome de exibição. Atividade é best effort a partir da presença em cache:
  não há intent privilegiado, busca de presença ou atualização contínua do nome.
- Painel com sala, proprietário e participantes. Saída do proprietário deixa a
  sala ocupada sem proprietário; sala vazia é removida com histórico `CLOSED`.
- Persistência Prisma/PostgreSQL, compensação de falhas, locks locais e shutdown
  que drena interações/eventos aceitos antes de fechar Discord/banco.

## Limitações operacionais

- **Todos os controles da call estão desabilitados:** renomear, limite,
  privatizar, assumir e moderação. Alternar `roomCommandsEnabled` no setup grava
  apenas a preferência e não os habilita nesta versão.
- O preflight do bot é conservador: requer Gerenciar Canais, Mover Membros e
  Conectar no servidor, acesso/envio no contexto do setup e permissões efetivas
  no canal/categoria. Sobrescritas locais isoladas podem ser insuficientes.
- Salas temporárias usam permissões públicas explícitas; negações específicas
  da categoria não são copiadas. Não use como mecanismo de salas privadas.
- Falhas ficam em logs seguros e, quando persistidas, em estados acompanhados
  (`CREATING`/`ACTIVE`/`CLOSING`). Novos eventos podem avançar limpeza/ativação;
  não há retry periódico nem **reconciliação no startup**. Se persistência e
  remoção do canal falharem, o ID fica em log para intervenção manual.
- Locks são locais ao processo, não uma garantia distribuída entre instâncias.
- Ownership avançado (assumir/transferir) fica para `v0.3.0`; moderação e
  reputação permanecem fora desta versão.

## Banco e verificação local

O schema inclui `VoiceCreator` e `TemporaryRoom`; a migration SQL está em
`prisma/migrations/20261105000000_v0_2_setup_join_to_create/migration.sql`.
Startup e testes **não aplicam migrations**. Preparar e migrar um banco é uma
operação separada, com destino explicitamente autorizado.

Verificação sem acesso a serviços externos (PowerShell):

```powershell
$env:RUN_DATABASE_TESTS = 'false'
npm test -- --run tests/integration/setup-calls-database.test.ts
npm run typecheck
npm run test:run
npm run build
git diff --check
```

O teste isolado deve informar **1 skipped**. A suíte completa mantém os dois
testes PostgreSQL pulados sem opt-in.

Para executar o round trip real, primeiro confirme um PostgreSQL **local e
descartável**, com schema desta versão já preparado. Configure `DATABASE_URL` e
`DIRECT_URL` na sessão para esse banco, sem reutilizar credenciais/URLs de
produção e sem expô-las em logs. A configuração atual do Vitest não carrega
`.env` automaticamente. Somente após confirmar o destino:

```powershell
$env:RUN_DATABASE_TESTS = 'true'
try {
  npm test -- --run tests/integration/setup-calls-database.test.ts
} finally {
  $env:RUN_DATABASE_TESTS = 'false'
}
```

O guard existente é apenas opt-in, **não valida que a URL seja segura/local**.
Não o habilite para um banco remoto, compartilhado ou de produção. O teste
exercita ambos os repositórios reais: duas configurações independentes,
atualizações de categoria/comandos, criar/ativar/limpar proprietário/encerrar,
exclusão lógica/restauração e retenção do histórico. A limpeza transacional em
`finally` remove somente os dados UUID do próprio teste, salas antes dos
creators; a desconexão é tentada mesmo se a limpeza falhar.

## Estado desta preparação

- Metadados npm preparados como `0.2.0`, sem tag.
- Não há banco local descartável confirmado nesta execução: o round trip real
  e a aplicação/validação SQL da migration **não foram executados**. Skipped não
  equivale a validação PostgreSQL bem-sucedida.
- Não houve smoke test Discord, registro de comandos, migrations remotas,
  escrita remota, push, merge, tag, publicação de release ou deploy.
- O script de registro inclui `/status` e `/setup init`, mas não roda no startup;
  executar o registro é uma operação remota separada que exige autorização.
