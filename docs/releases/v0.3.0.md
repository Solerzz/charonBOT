# Charon v0.3.0 — posse e controles

**Preparação local em 2026-11-09; não publicada/deployada.** Design/plano
aprovados em 2026-11-08, nove gates por tarefa aprovados, incluindo o fix I1 da
Task 9. A revisão final da branch aguarda o controlador. Não houve tag, push,
merge, login do bot ou DDL remoto.

## Entrega implementada

1. Painel B nativo público e menu privado do dono: renomear (11 grafemas),
   limite `0`/ilimitado ou `1..99` sem kick, privacidade e autorizados.
2. Transferência para humano presente/elegível: prompt privado confirmado
   inicia exatamente 5.000 ms; dono confirma/desfaz ou silêncio transfere.
   Destinatário não aceita/autoriza a operação. Um dono por servidor nas salas
   `CREATING`/`ACTIVE`/`CLOSING`, protegido por índice parcial SQL.
3. Sala sem dono: humano continuamente presente elegível mais antigo tem
   prioridade exclusiva de 300.000 ms; depois abre a qualquer elegível presente.
   Saída após expiração não reinicia esse prazo.
4. Privado permite dono + presentes + allowlist; saída de não autorizado
   revoga acesso. Allowlist sobrevive a transferência e público/privado.
5. Setup off remove painel inteiro/invalida menus/cancela transferência;
   privacidade/presença/prioridade continuam. On restaura painel. Timer de
   prioridade acompanha nova geração sem mudar candidato ou deadline.

## Permissões e limites operacionais

- Setup administrativo exige Administrador ou Gerenciar Servidor + Gerenciar
  Canais. O bot precisa Gerenciar Canais, Mover Membros, **Gerenciar Cargos**,
  Conectar e acesso/envio operacional; preflight conservador pode rejeitar
  permissões concedidas apenas por sobrescritas locais. **Administrador ignora
  negações de acesso privado**: não há promessa de ocultação desses membros.
- **Um processo apenas.** Reinício cancela transferências antigas, invalida
  menus e reobserva salas acompanhadas; não reconstrói ordem de entradas offline,
  não varre todo o servidor e não resolve todos os órfãos. Shutdown fecha
  admissão/drena handlers e timers antes de liberar Discord/DB.
- Discord/SQL têm compensação, não atomicidade entre sistemas. Nome anterior
  exato (inclusive externo) e sobrescritas preservando bot são restaurados quando
  possível; falha de compensação gera erro seguro/IDs, nunca fallback público
  silencioso. Mutações externas repetidas, replies incertos, cleanup de painel
  duplicado e órfãos podem exigir sincronização/intervenção posterior.
- Storage indisponível na expiração: retry **somente para cancelar** UUID
  original a cada 1 s enquanto processo vive; sem novo prazo ou replay de commit
  incerto. Outage persistente não garante transferência. Startup cancela sobras.
- Sem moderação/reputação. Figma draft não é entregável/verificação visual
  (limite de leitura MCP Starter); implementação nativa é a referência. Latência
  de abertura de modal contra deadline Discord de três segundos ainda é manual.

## Banco local e CI (sem credenciais remotas)

Migrations antigas são imutáveis. Ordem atual:

1. `prisma/migrations/20261105000000_v0_2_setup_join_to_create`
2. `prisma/migrations/20261108000000_enable_backend_table_rls`
3. `prisma/migrations/20261108010000_room_ownership_state`

As seis tabelas (`VoiceCreator`, `TemporaryRoom`, `_prisma_migrations`,
`RoomPresence`, `RoomAllowedMember`, `PendingOwnershipTransfer`) têm RLS sem
políticas públicas, backend-only. Data API Supabase desabilitada é estado
preexistente, não uma alteração desta preparação.

Provisione PostgreSQL 17 **descartável local** antes dos comandos abaixo. Injete
`DATABASE_URL` e `DIRECT_URL` no processo, mesmo banco/credenciais/porta loopback,
nome `charon_v030_test...`, sem query ou apenas `?schema=public`. Não carregue
`.env` remoto. Não publique URLs/senhas nos logs. O guard não cria banco.

```bash
npm ci
node --import tsx --input-type=module -e "import { assertDisposableDatabaseEnvironment as guard } from './tests/integration/database-test-utils.ts'; guard();" && npm run prisma:generate
node --import tsx --input-type=module -e "import { assertDisposableDatabaseEnvironment as guard } from './tests/integration/database-test-utils.ts'; guard();" && npx --no-install prisma migrate deploy
node --import tsx tests/integration/prepare-database.ts
RUN_DATABASE_TESTS=true RUN_DATABASE_SECURITY_TESTS=true npm run test:run -- tests/integration --maxWorkers=1
node --import tsx --input-type=module -e "import { assertDisposableDatabaseEnvironment as guard } from './tests/integration/database-test-utils.ts'; guard();" && npx --no-install prisma migrate status && npx --no-install prisma migrate deploy
```

As atribuições inline são Bash; no PowerShell configure somente esses dois flags
no processo (`$env:RUN_DATABASE_TESTS='true'` e
`$env:RUN_DATABASE_SECURITY_TESTS='true'`) antes do comando npm. Pare em qualquer
falha. `prepare-database.ts` valida o guard antes dos grants/roles locais anon e
authenticated. Testes limpam somente fixtures UUID próprias. Sem reset, truncate
ou suite mutante remota. `--maxWorkers=1` é necessário porque startup reconcilia
todas as salas acompanhadas do banco compartilhado.

CI conserva o job comum sem serviço e acrescenta job PostgreSQL 17 com porta
loopback e credenciais efêmeras sem secrets remotos. Geração, deploy, grants,
ambos opt-ins, status e segundo deploy estão declarados. Comandos equivalentes
passaram localmente; execução hospedada GitHub ainda não foi observada.

**Deploy Supabase é uma ação futura separada:** confirmar destino/backup e
autorizar explicitamente antes de aplicar migrations pendentes. Não modificar
migrations publicadas, não substituir essa etapa por testes destrutivos remotos.
