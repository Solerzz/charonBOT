## Global Constraints

- One active/non-closed room per owner **per guild**, including tracked `CREATING`/`ACTIVE`/`CLOSING` rows.
- Rename: trimmed, nonempty, <=11 graphemes. Limit: integer 0 or 1–99; never kick on reduction.
- Transfer: 5,000 ms, current owner retains possession until confirmation/timeout; undo cancels; no recipient acceptance. Owner/target departure or disabled controls invalidates it.
- Claim: 300,000 ms exclusive priority for the longest continuously present eligible human, then open claim. A departure before expiry gives the next eligible person a fresh window.
- Compact public panel B; owner-only private menu. No new slash commands, moderation, reputation, dashboard, Redis or multi-process coordination.
- Controls off removes the whole panel and cancels pending transfers; controls on restores existing and future rooms. Do not change room privacy on toggle.
- Private access: owner/current participants/room-specific allowlist, with Discord Administrator bypass acknowledged. No public RLS policies; retain the bot's access.
- No production code before its failing test; use fake timers, not real five-second/five-minute waits, in unit tests.
- Do not expose `.env`, decoded passwords, certificate contents/paths in public output, or interaction payloads in logs.
- No Supabase DDL, Discord login, command registration, deployment, push, tag publication or hosting without separate confirmation. All data-changing tests use a disposable local database.

## Review Focus

1. Timer/confirm/undo/departure/close/setup races must produce at most one transfer and must not make an old owner's controls valid again after a later ownership cycle.
2. A departure **after** claim priority expires must not accidentally start another exclusive window; eligibility changes before expiry must not starve the next eligible human.
3. Discord permission or database failure must not report a private room while silently granting broader access, or leave an invisible transfer scheduled after a failed private response.
4. Setup toggle, deleted public messages, logically deleted creators and stale private menus must not produce duplicate tracked panels or revive disabled controls.
5. Stop during startup, timers waiting on locks and startup reconciliation must not deadlock or execute after Discord/database disposal.

Tests for these conditions are assigned below to their owning tasks, not deferred to manual smoke testing.


Every CAS requires the expected version, tracked room identity and appropriate status. `read` includes the related creator even when logically deleted, preserving its last controls preference. `changeOwner` and `finishTransfer` update ownership, increment `controlVersion`, clear priority and delete the pending transfer in **one SQL transaction**. Setting a non-null owner requires `ACTIVE` and controls enabled; clearing an owner must still work when controls are off and can preserve recovery behavior for non-closed rows. Translate the active-owner unique-index conflict to `ALREADY_OWNS_ROOM`.

Transfer preparation has `expiresAt=null` and cannot automatically complete. After successful initial private-response delivery, `armTransfer` changes null to now+5,000 ms once, validates version/owner/configuration and schedules it. This provides five usable seconds and prevents invisible automatic transfers if publishing fails. A user's explicit valid confirmation may complete the prepared row immediately; timeout completion requires a non-null elapsed deadline. User undo can cancel a prepared row or an unexpired armed row; only internal failure cleanup uses `discardTransfer`, scoped to that exact operation ID. No other pending row is deleted by a late response failure.

### Lock and permission contracts

- `RoomCoordinator` wraps one `KeyedMutex`: `member<T>(guildId, memberId, work:()=>Promise<T>):Promise<T>` uses the existing `${guildId}:${memberId}` key; `room<T>(guildId, channelId, work):Promise<T>` uses `room:${guildId}:${channelId}`.
- Acquire at most one member lock followed by one room lock. Claims lock the claimant; begin/undo lock the initiating owner; confirm/expiry lock the **recipient**. Never acquire a member lock while already holding a room lock, or hold two member/room locks.
- Methods suffixed `Locked` are actual production collaborators called by the lifecycle/runtime while the shared room lock is already held. They must not reenter the non-reentrant mutex.
- `requireActiveRoom(store, actor, gateway):Promise<{state:RoomState;snapshot:RoomSnapshot}>` and `requireOwnedRoom(...)` live in `room-context.ts`. Check guild/channel, ACTIVE status, presence, controls flag and `controlVersion`; the owner variant additionally checks current ownership. Read live gateway state, not event-time member-count snapshots.
- `RoomChanged` runs after the SQL commit, still under the room lock, to synchronize private permissions and panel. It never opens another member/room lock or holds a database transaction over Discord I/O.
